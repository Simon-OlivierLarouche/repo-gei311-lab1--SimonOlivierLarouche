1. PARTIE 2-1 : SITUATION 1 - PASSAGE D'UN REPO LOCAL VERS GITHUB

Problématique :
Le Membre A a créé un repository en local avec ses commits initiaux, 
sans créer au préalable de projet sur GitHub. L'objectif est de rendre 
ce projet accessible sur GitHub et de permettre la collaboration de B.

Étapes de résolution :
1. Création du repository distant (Membre A) :
   - Sur GitHub, création d'un nouveau dépôt public vide nommé :
     "partie2-lab-SOL" 

2. Liaison du repository local vers GitHub (Membre A) :
   - Dans le terminal local, positionnement dans le projet.
   - Renommage de la branche principale par convention :
     git branch -M main
   - Ajout de l'URL du repository GitHub comme remote :
     git remote add origin <URL_GITHUB_DU_REPO>
   - Envoi du code et configuration du suivi distant :
     git push -u origin main

3. Ajout du collaborateur Membre B (Membre A) :
   - Sur GitHub : Settings > Collaborators > "Add people".
   - Recherche et invitation du compte GitHub du Membre B.

4. Récupération et travail en collaboration (Membre B) :
   - Membre B accepte l'invitation reçue par courriel ou via GitHub.
   - Membre B clone le repository pour commencer le travail collaboratif :
     git clone <URL_GITHUB_DU_REPO>


2. PARTIE 2-2 : SITUATION 2 - GESTION DES ERREURS ET HISTORIQUE

Problématique :
Le Membre B a injecté une erreur non compilable/invalide ("erreur injectée") 
dans Dossier_A/textA.txt, puis a poursuivi avec un autre changement valide 
(Dossier_B/textB2.txt). Le Membre A a signalé l'anomalie via une Issue. 
Le Membre B doit annuler l'erreur sans perdre le travail valide ultérieur.

Étapes de résolution :
1. Identification et traçabilité de l'erreur :
   - Le Membre A a ouvert une issue GitHub décrivant la présence de la 
     ligne "erreur injectée" dans Dossier_A/textA.txt.
   - Le Membre B a consulté l'historique de commits et a répondu sur l'issue :
     * Commit problématique : commit correspondant à l'étape 6 (ajout de l'erreur).
     * Dernière version fonctionnelle : commit correspondant à l'étape 5 
       (création de Dossier_B/textB.txt avec "collaboration avec A").

2. Consultation de l'historique local en ligne de commande (Membre B) :
   - Commande exécutée pour visualiser les hashs des commits :
     git log --oneline

3. Retour à la version saine et nettoyage (Membre B) :
   - Revenir à l'état du dernier commit sain avant l'erreur (étape 5) :
     git reset --hard <HASH_COMMIT_ETAPE_5>
     (Ou utilisation de "git revert <HASH_COMMIT_ERREUR>" pour annuler 
     strictement le commit contenant l'erreur injectée).

4. Réapplication des changements valides non erronés (Membre B) :
   - Réintégration du changement prévu à l'étape 7 :
     Création de "Dossier_B/textB2.txt" contenant la phrase "autre changement de B".
   - Enregistrement du nouveau commit propre :
     git add Dossier_B/textB2.txt
     git commit -m "Ajout de textB2 sans erreur injectee"

5. Synchronisation distante :
   - Mise à jour du repository GitHub avec la version corrigée :
     git push origin <NOM_BRANCHE> (ou git push --force si reset local utilisé).


3. SECTION BILAN ET README (EXPÉRIENCE & CHEAT-SHEET)

Résumé des apprentissages :
Ce premier travail pratique m'a initié aux mécanismes concrets du travail collaboratif sous Git et GitHub. 
J'ai pu observer comment l'isolation des tâches sur des branches distinctes évite d'altérer la branche principale durant le développement. 
Les exercices m'ont sensibilisé à l'importance de rédiger des messages de commit précis afin d'assurer une traçabilité rigoureuse à chaque jalon du projet. 
Sur le plan pratique, l'utilisation répétée des commandes de synchronisation (push/pull) m'a permis de maîtriser l'alignement entre l'espace de travail local et le dépôt distant. 
Enfin, les mises en situation m'ont exercé à deux aspects essentiels : la transition d'un projet local non versionné vers un environnement partagé en ligne, ainsi que la gestion des régressions de code grâce aux mécanismes de restauration de commits stables.


Aide-mémoire Git (Cheat-Sheet) :
Configuration & Initialisation :
- git config --global user.name "..."  : Permet l'enregistrement l'identité de l'auteur des commits.
- git config --global user.email "..." : Associe une adresse de contact aux contributions.
- git init                            : Crée un nouveau dépôt Git local dans le répertoire courant.
- git clone <URL>                     : Télécharge localement l'intégralité d'un projet distant avec son historique.
- git remote add origin <URL>         : Établit le lien réseau entre le dossier local et le serveur GitHub distant.

Suivi & Validation des modifications :
- git status                          : Contrôle l'état des fichiers (modifiés, indexés ou non suivis).
- git add -A (ou --all)               : Place la totalité des modifications en zone de préparation (staging area).
- git commit -m "..."                 : Fige les fichiers préparés dans un nouvel instantané horodaté et commenté.
- git log --oneline --graph           : Génère une vue synthétique et visuelle de la chaîne des commits.

Branches & Fusion :
- git branch                          : Affiche l'inventaire des branches locales actives.
- git switch <branche>                : Bascule sur l'espace de travail de la branche cible.
- git switch -c <branche>             : Crée une branche dérivée et s'y positionne immédiatement.
- git merge <branche>                 : Intègre les modifications de la branche indiquée dans la branche courante.

Synchronisation & Dépannage :
- git push -u origin <branche>        : Transfère la branche locale vers GitHub et configure le suivi distant.
- git pull                            : Rapatrie et applique les nouveaux commits distants sur la branche locale.
- git reset --hard <commit_id>        : Réinitialise l'arbre de travail et l'index à l'état exact du commit visé.
- git revert <commit_id>              : Génère un commit inverse pour annuler proprement les changements ciblés.

Commandes d'environnement (CLI & Shell) :
- mkdir <nom>                         : Génère un nouveau répertoire sur le système de fichiers.
- echo "texte" > fichier.txt          : Crée ou écrase un fichier avec la chaîne de caractères fournie.
- Add-Content fichier.txt "texte"     : Concatène du texte en fin de fichier existant (PowerShell).
- Get-Content fichier.txt             : Lit et affiche l'intégralité d'un fichier dans la console (PowerShell).

Retour d'expérience sur les Issues :
Une issue sert à signaler et à documenter un problème au sein du projet. J'ai appris qu'une issue doit être rédigée de manière claire et précise afin qu'un membre de l'équipe puisse comprendre rapidement la situation :
- Titre : Doit être explicite et résumer le problème en quelques mots.
- Description : Doit préciser la source du problème, les étapes pour reproduire le comportement inattendu ainsi qu'un résumé du comportement attendu vs observé.
- Traçabilité : Doit mentionner la version (commit hash) ayant introduit l'erreur ainsi que la dernière version stable fonctionnelle pour faciliter l'investigation et le rollback.
