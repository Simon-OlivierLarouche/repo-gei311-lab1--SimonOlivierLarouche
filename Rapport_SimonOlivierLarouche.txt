Situation 2-1 
Pour cette situation, le projet existait initialement seulement sur l’ordinateur local et aucun repository n’avait encore été créé sur GitHub.
J’ai d’abord créé le dossier du projet et j’ai initialisé Git avec la commande git init. J’ai ensuite créé la même structure que dans la partie 1
avec le dossier Dossier_A et le fichier textA.txt. Les fichiers ont été ajoutés à Git et un premier commit local a été effectué avec git add --all
et git commit -m "". Puisque la collaboration avec le membre B était nécessaire, un repository vide a ensuite été créé sur GitHub. J’ai relié le 
repository local au repository distant avec git remote add origin URL. Le repository local a ensuite été envoyé sur GitHub avec git push -u origin main
Une fois le projet disponible sur GitHub, le membre B pouvait accéder au repository et le cloner. Cette situation m’a permis de comprendre comment 
partir d’un projet uniquement local et le rendre accessible à un coéquipier à l’aide de GitHub.

Situation 2-2
Pour cette situation, j'ai d’abord créé le repository sur GitHub, puis je l'ai cloné localement. J'ai créé Dossier_A et textA.txt, puis effectué un commit et un 
push vers GitHub. Le membre B a ensuite cloné le repository et créé Dossier_B ainsi que le fichier textB.txt. Il a ensuite effectué un premier commit. Après ce premier commit, le membre B a ajouté volontairement la ligne « erreur injectée » dans Dossier_A/textA.txt et a créé un nouveau commit pour cette modification. Le membre B 
a ensuite créé le fichier Dossier_B/textB2.txt contenant la phrase « autre changement de B » et a effectué un autre commit. Les changements ont ensuite été 
synchronisés avec le repository distant. J'ai ensuite créé une issue sur GitHub afin de signaler la présence de la ligne « erreur injectée » dans Dossier_A/textA.txt. L’issue décrivait le problème. Le membre B a ensuite consulté l’historique des commits et ceci lui a permis d’identifier le commit problématique ainsi que la dernière version fonctionnelle. J'ao utilisé l’historique des commits pour revenir à la dernière version non erronée.

Cette situation m’a permis de comprendre comment utiliser les issues pour identifier un mauvais commit et revenir à une version fonctionnelle.


Git Cheat-Sheet:

Git config --global user.name "" : Permet de définir un nom

Git config --global user.email "" : Permet de définir l’adresse courriel

Git clone URL : Permet de copier un repository distant à partir de l'URL

Git init   : Initialise le dossier courant comme un repository Git local

Git status : Affiche l'état d'un repository

Git remote add origin URL : Relie un repository local à un repository distant

Git add --all : Ajoute tous les changements 

Git commit -m "message" : Crée un commit avec les changements effectués. Permet de documenter un changement

Git push origin main : Envoie les commits de la branche main vers le repository distant

Git pull : Synchronise les changements du repository distant à la branche locale

Git branch : Donne la liste des branches existantes

Git checkout Nom_branche : Permet de changer de branche 

Git checkout -b Nom_branche : Permet de créer une nouvelle branche

Git merge Nom_Branch : Permet de fusionner une branche avec la branche active

Git log : Affiche l'historique des commits

Git reset --hard Numero_commit : Permet de revenir à l’état d'un commit précédent

Git switch Nom_Branch : Permet de changer de branche


Pas des commandes Git mais important pour nos futurs projets : 

mkdir Nom_Dossier : Crée un dossier

echo "texte" > text.txt : Crée un fichier texte contenant le texte indiqué

Add-Content text.txt "texte" : Ajoute du contenu à un fichier existant

Get-Content text.txt : Affiche le contenu d’un fichier

Issue : 

Une issue sert à signaler et à documenter un problème. J'ai appris qu'une issue doit être claire et précise afin qu'un autre membre puisse comprendre le problème facilement.
Une issue doit avoir un titre clair. La description doit contenir la source du problème et une courte description du problème observé. Une description doit également contenir la version du commit
erroné ainsi que la dernière version utilisable. Une issue doit toujours être bien structurée et claire pour faciliter la communication entre les membres de l'équipe.
